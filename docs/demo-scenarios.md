# 16シナリオ

共通準備：DB→migration→devを起動し、Portalで隔離デモを開始する。右上の人物選択で利用者・加盟店・運営者へ切替。初期残高・店舗・商品は「サンプル」。デモ操作パネルに残高、provider attempt、job、outbox、APIログ、台帳整合性を表示する。

|番号|操作|期待結果|
|---|---|---|
|1|ECへ接続、即時確定で商品購入、ウォレット承認、店舗へ戻る|ECが照会・capture、Webhook後も支払済み・発送1件|
|2|支払元に模擬Visaを選択、確定後ECまたは加盟店から部分返金|財布を増減せず元provider tokenへ返金|
|3|残高を超える注文、承認で不足、チャージ後同じcheckoutを再承認|最初は残高移動なし、再承認で確保|
|4|承認後にタブを閉じ、EC購入履歴から照会・更新|URLの成功パラメータなしで回復|
|5|出荷時確定でオーソリだけ作成、時計を90,000秒進める|workerがexpire、未確定保留を解放|
|6|商品2個購入、半額capture＋final、部分返金|半額だけ確定、未使用分解放、確定分内で返金|
|7|オーソリ後に加盟店へ切替、デモの100並列パネルで対象と金額を選び「同じ冪等キー」を確認・実行|100応答でもcapture1件、仕訳1回。別キーでは累計上限まで|
|8|ECで2件の未承認注文を作成しcheckout URLを控える。利用者のデモパネルに両URLを入力し金額確認・同意後に同時承認|残高を超えて両方は成功しない。DBテストは10,000円から8,000円2件、UIテストは30,000円から24,000円2件|
|9|worker停止中にチャージ、attemptへtimeout_success、worker再開|unknown→照会成功、仕訳1回|
|10|EC購入履歴で次のWebhookを500に設定、決済|失敗deliveryの後に新deliveryで成功|
|11|古い成功通知を開発者ポータルから再送|event重複/最新照会により状態が後退せず発送増加なし|
|12|worker停止中に加盟店出金、attemptをdecline、再開|payout failed、出金保留解放|
|13|精算後に加盟店残高を出金、全額返金、模擬追加入金後再試行|原資不足を明示、自動立替せず回復|
|14|プラン/同意待ち購読作成、利用者同意、残高不足、入金＋1日進める|past_due→同一周期再試行成功。撤回なら新規請求なし|
|15|運営者で利用者can_payだけをfalse|新規支払い不可、過去明細と返金受取は可能|
|16|別人物/別workspaceのリソースをAPIで照会|403/404、他workspaceの残高不変|

金融操作の結果を一括成功にするボタンはない。providerの結果指定は対象attemptを選び、完了していない操作にのみ行う。高速操作で失敗注入が間に合わない場合、workerを個別に止めてから申請する。システム時計は変更しない。

「操作前後を比較」で現在の残高・オーソリ・台帳・APIログ・配信履歴を読み取り保存できる。通常画面で操作後に戻り「操作後を取得」。比較は同じブラウザタブのメモリーに保持し、再読み込みで消える。workspace/generation別に分離し、PWAキャッシュには保存しない。

現在の自動化範囲・未実施検証は [implementation-status.md](implementation-status.md) に記録する。テストを実行していないシナリオを合格とは扱わない。
